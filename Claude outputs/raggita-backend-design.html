RagGita Backend Design

Turning a stateless single-container chat endpoint into a multi-user backend with per-user history, conversation memory, and the compliance an Indian mental-health app needs before it reaches the Play Store.

auth · Firebase memory · window + summary scale · ~200 users retention · user-deletable store · DynamoDB

What actually changes

The Lambda you have today answers each message in isolation. It does not know who is asking, and nothing survives the request. Three things have to be added, and only three: identity, storage, and memory. Everything else already works — the RAG retrieval, the class router, the crisis guard, the voice endpoints.

Already built

The crisis guard, the seven-class dynamic prompting, the 60–90 word reply discipline and the Web Adapter deployment all carry forward unchanged. This design adds a layer around them rather than replacing them.

Deliberately not changing: the Function URL stays the entry point, the FastAPI app stays one Lambda, and there is no second service. At a few hundred users, splitting this into microservices would add failure modes and buy nothing.

The path a message takes

The order matters. Token verification first, because everything downstream is keyed on uid. Crisis check before the model, because that reply is fixed text and must work even when quota is exhausted or OpenAI is down.

Identity without an API Gateway

The Android app signs in through Firebase (Google or phone OTP) and gets an ID token — a short-lived RS256 JWT that the SDK refreshes on its own. Every request carries it as Authorization: Bearer <token>.

Lambda verifies it in-process: fetch Google's public signing keys once per cold start, cache them, check signature, expiry, issuer and audience against your Firebase project id. The sub claim becomes your uid. No network call per request.

Why not API Gateway

API Gateway with a Cognito or Lambda authorizer is the textbook answer, and it is the wrong one here. It adds per-request cost, a second place for CORS and timeouts to be wrong, and a streaming configuration you already fought once. Verifying a JWT is about forty lines. Revisit this if you ever need usage plans, API keys for partners, or WAF.

Cold start trick

Fire GET /health the moment the app opens, before the user types anything. By the time they have written a sentence, the container is warm and the first reply feels instant instead of taking eight seconds. It costs one cheap invocation.

One table, two access patterns

Everything the app reads falls into two questions: what chats does this user have, and what was said in this chat. A single DynamoDB table answers both with one query each, which is the whole reason to shape the keys this way rather than reach for Postgres.

Turn on point-in-time recovery and leave the table on on-demand capacity. At this scale you will never think about throughput again, and you pay for what you use. The ttl attribute on quota rows lets DynamoDB expire yesterday's counters for free.

Memory that does not grow without bound

You chose recent messages plus a long-term summary. The reason that combination matters is cost: a naive "send the whole history" approach makes every message more expensive than the last, and a long conversation eventually costs more than the user is worth.

The per-user longTermSummary on the profile row is the slower loop: a few lines about what this person keeps returning to, refreshed rarely. It is what makes the app feel like it knows them across weeks rather than within one session.

Write this one carefully

The summariser prompt decides what gets remembered about someone's worst nights. Tell it to record situations and what helped, and explicitly not to record diagnoses, self-harm details, or anything it inferred rather than heard. A summary is the one artefact that outlives the conversation, so it is the one most worth getting wrong slowly.

Per-user limits, because the current ones do not work here

The rate limiter you shipped counts requests in process memory. On Lambda each concurrent container has its own counter, so the real limit is your setting multiplied by however many containers happen to be warm. It was always a backstop; with identity you can do it properly.

Use a DynamoDB atomic counter: one row per user per day, UpdateItem with ADD count 1 and a condition that rejects the write past the cap. It is a single round trip, it is correct across every container, and the ttl attribute deletes yesterday's rows without a cleanup job.

Keep the limit generous — someone having a hard night may send thirty messages, and that is not abuse. The cap exists to stop a runaway client or a scripted attack, not to ration comfort. And as it does today, the crisis path skips the check entirely.

Crisis handling, with real users

Right now the guard returns a helpline and that is the whole system. With accounts, history and a Play Store listing, you will be tempted to build more: alerts, escalation, a dashboard of at-risk users. Think hard before you do.

The honest constraint

An app that implies someone is watching, when nobody is, is more dangerous than one that plainly is not. If you cannot staff a human response within minutes, every hour of the night, do not build anything that suggests you can. Surface the helpline well and be clear about what the app is.

  • Put Tele-MANAS 14416 in the app's permanent chrome — a corner of the screen, not only inside a reply someone has to earn.
  • Log crisis events (uid, timestamp, that it fired) and never the message text. You want to know the guard works; you do not want a database of people's worst moments.
  • Consider not persisting crisis messages at all. The user loses nothing; you lose a liability.
  • Tune the guard with real misses, not imagination. Its failure mode should stay "too many false positives".

There is also an age problem worth naming now. A free Indian mental-health app will be used by people under eighteen, and DPDP requires verifiable parental consent for children's data. There is no clean answer — decide deliberately rather than discovering it during review.

What the law actually asks for

Two regimes apply, and both have real dates. Chat logs from a mental-health app are about the most sensitive category of personal data you can hold, so this is not paperwork to do at the end.

  • Consent notice in plain language, English plus at least Hindi — tell people their conversations are stored and why.
  • Deletion that really deletes. DELETE /me must remove messages, summaries and the profile row, not just hide them.
  • Grievance officer — a real, publicly reachable contact. For a solo developer that is you, with an email that is monitored.
  • Never log message bodies to CloudWatch. Logs are the easiest place for sensitive text to leak into a system nobody audits.
  • Encryption is on by default in DynamoDB and in transit. Leave it on and say so in the policy.

You are almost certainly not a Significant Data Fiduciary at this size — that threshold sits around five million users — so the audit obligations do not apply yet.

What I would not build

Each of these is the standard answer to a problem you do not have. Skipping them is the design decision, not an omission.

  • API Gateway — the Function URL already streams and already works.
  • A VPC — adds cold-start latency and NAT cost; DynamoDB and OpenAI are both reached over the public internet anyway.
  • Redis or any cache — DynamoDB answers in single-digit milliseconds and you have no read hotspot.
  • SQS or async workers — a chat reply is synchronous by nature; the user is waiting.
  • Postgres or RDS — an always-on instance under a serverless app, for access patterns a key-value store already fits.
  • WebSockets — SSE over the Function URL covers streaming replies.
  • Multiple Lambdas per endpoint — one FastAPI app is easier to reason about and shares one warm container.
